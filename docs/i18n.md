# Internationalisation (i18n)

Library: [next-intl](https://next-intl.dev) 4.x, **without locale routing** (URLs are the same in every language; the UX session owns the `app/` paths).

## Locales

`es` (canonical content), `en` (default UI), `fr`, `pt-BR`, `it`, `de`, `ar` (RTL), `zh-Hans`, `hi`, `ru`, `uk`, `tr`.
Source of truth: `lib/i18n/locales.ts` (list, native names, RTL flag, Accept-Language matcher).

## How the locale is chosen

`i18n/request.ts` (wired in `next.config.ts` via `createNextIntlPlugin`):

1. `NEXT_LOCALE` cookie, if it holds a supported locale;
2. otherwise the best match for the `Accept-Language` header (`pt` → `pt-BR`, `zh` → `zh-Hans`);
3. otherwise `en`.

Messages are deep-merged over `messages/en.json`, so a missing key in a translation falls back to English instead of breaking the page.
`app/layout.tsx` sets `<html lang dir>` (`dir="rtl"` for Arabic) and wraps the app in `NextIntlClientProvider`.

`components/i18n/LocaleSwitcher.tsx` is a ready-made `<select>` that writes the cookie and calls `router.refresh()`. Screens decide where to place it.

## Message keys

Files: `messages/<locale>.json`. Keys are namespaced `<screen>.<element>`:

| Namespace | Example keys |
|---|---|
| `nav` | `home`, `tasks`, `city`, `chat`, `profile` |
| `design` | `chart`, `minimal`, `label` |
| `onboarding.welcome` | `headline1..3`, `body`, `cta`, `demoTitle`, `demoNote` |
| `tasks.header` | `title` (`{city}`, `{name}`), `progress` (ICU plural on `{total}`, plus `{done}`) |
| `step.actions` | `start`, `markDone`, `undo`, `finishFirst` (`{steps}`) |
| `common` | `verifiedSource` (`{date}`), `sourcePending`, `todoVerify` |
| `locale` | `label` |

Usage in a client component:

```tsx
import { useTranslations } from "next-intl";

const t = useTranslations("tasks.header");
t("title", { city: "Madrid", name: "Priya" });
t("progress", { done: 3, total: 11 });
```

Server components: `const t = await getTranslations("tasks.header")` from `next-intl/server`.

Add new keys to `messages/en.json` first (English is the fallback), then to the other files. Every non-English, non-Spanish file carries `"_meta": {"status": "machine-translated, needs native review"}`; remove it once a native speaker has reviewed the file.

## RTL (Arabic)

- Use **logical** CSS properties so layouts mirror automatically: Tailwind `ms-*`/`me-*`, `ps-*`/`pe-*`, `start-*`/`end-*`, `text-start`/`text-end`, `border-s`/`border-e`, `rounded-s`/`rounded-e`. Avoid `ml/mr/pl/pr/left/right` for layout.
- Directional icons (arrows, chevrons) should flip in RTL: `rtl:-scale-x-100`.
- Numbers, dates and official codes (e.g. `790-012`, `EX-17`) stay left-to-right; wrap them in `<bdi>` or `dir="ltr"` when mixed into Arabic text.
- Charts drawn in SVG (the day rail, arcs) keep their geometry; only their text labels follow the locale.

## Content translation policy

- **Spanish is canonical** for procedure content: requirements, deadlines, fees, official names and the official source with its last-verified date.
- Official procedure and app names are **never translated** (e.g. *Empadronamiento*, *TIE*, *Abono Joven*, *Cl@ve*); the UI may add a short explanation in the user's language.
- Translations of verified content are shown **marked as translations**, linked to the Spanish source and its date, and are **regenerated when the source or its verification date changes**. A translation never carries a "verified" badge of its own.
- The assistant answers in the user's language but cites the official (Spanish) source and date.
